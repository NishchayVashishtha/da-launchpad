## Project overview & business context

In consumer fintech and unified payments interface (UPI) ecosystems, payment reliability is the foundation of user retention. If a user experiences two consecutive payment failures at a merchant checkout counter, they switch to a competing payment app or default back to cash.

This project examines an enterprise transactional database containing **22,389 payment records**, 4,010 users, 400 merchants, and 607 failed transaction diagnostic logs across 8 major Indian partner banks.

The primary project objectives are:
1. Conduct rigorous data hygiene to eliminate duplicate transaction logs and correct decimal entry outliers.
2. Isolate systemic technical infrastructure failures from user-induced balance errors.
3. Identify partner banks and payment apps that breach regulatory uptime service level agreements (SLAs).
4. Analyze transaction anomaly flags to identify high-risk fraud patterns across time of day, merchant categories, and ticket sizes.

## Dataset architecture & schema inspection

The dataset models a complete payment switch processing ledger:
- `transactions` (22,389 rows): Transaction logs recording `txn_id`, user IDs, merchant IDs, receiver IDs, transaction types (P2P vs P2M), timestamps, amounts in INR, payment apps (PayZippy, QuickPaisa, NammaPay, SabPay, RupeeRocket), partner banks, device operating systems, transaction statuses (SUCCESS, FAILED, PENDING), and risk flags (`is_flagged = 1`).
- `failed_transactions` (607 rows): Failure root cause records capturing failure codes (`INSUFFICIENT_FUNDS`, `NPCI_DECLINE_TIMED_OUT`, `BANK_SWITCH_OFFLINE`, `INVALID_PIN`), failure descriptions, and retry status.
- `users` (4,010 rows): User master accounts, primary bank associations, KYC status tiers, and signup dates.
- `merchants` (400 rows): Business profiles, merchant category codes (MCC), onboarding dates, and verification flags (`is_verified = 1`).

## Data cleaning & hygiene checks

Auditing the raw payment records revealed three critical data hygiene issues:

1. **Duplicate Transaction Pings**: 90 duplicate transaction rows caused by client-side retry pings during network handoffs.
2. **Pricing Outliers**: 6 transactions contained amounts inflated by 100x (e.g., `Rs 550,000` recorded for a Rs 5,500 grocery merchant bill).
3. **Inconsistent App Naming**: Trailing whitespace and mixed casing in payment app and bank strings (`'nammaPay'`, `' NammaPay'`, `'kaveri co-op bank'`).

The following SQL script produces a clean, sanitized transaction view:

```sql
-- Step 1: Create deduplicated and sanitized payment transaction view
CREATE VIEW clean_transactions AS
WITH deduplicated AS (
  SELECT DISTINCT *
  FROM transactions
)
SELECT
  txn_id,
  user_id,
  merchant_id,
  receiver_user_id,
  txn_type,
  txn_datetime,
  CASE 
    WHEN amount > 100000 THEN amount / 100.0
    ELSE amount 
  END AS clean_amount,
  TRIM(payment_app) AS payment_app,
  TRIM(bank) AS bank,
  UPPER(TRIM(device_os)) AS device_os,
  status,
  is_flagged
FROM deduplicated;
```

## SQL exploratory & diagnostic analysis

### 1. Bank switch failure rates and error code diagnostics

Evaluating transaction success rates across commercial banks exposes stark operational discrepancies:

```sql
SELECT 
  bank,
  COUNT(*) AS total_transactions,
  SUM(CASE WHEN status = 'FAILED' THEN 1 ELSE 0 END) AS failed_transactions,
  ROUND(100.0 * AVG(CASE WHEN status = 'FAILED' THEN 1 ELSE 0 END), 2) AS failure_rate_pct,
  ROUND(SUM(CASE WHEN status = 'SUCCESS' THEN clean_amount ELSE 0 END), 0) AS successful_volume_inr
FROM clean_transactions
GROUP BY bank
ORDER BY failure_rate_pct DESC;
```

**Empirical Results:**
- **Kaveri Co-op Bank**: 1,700 transactions, 104 failures -> **6.11% failure rate** (industry outlier!).
- **PayNova Small Finance Bank**: 782 transactions, 23 failures -> **2.94% failure rate**.
- **Coromandel Bank**: 1,959 transactions, 52 failures -> **2.63% failure rate**.
- **Sundaram Bank**: 4,658 transactions, 121 failures -> **2.59% failure rate**.
- **Bharat Union Bank**: 5,097 transactions, 121 failures -> **2.37% failure rate**.
- **Rajdhani National Bank**: 3,712 transactions, 81 failures -> **2.18% failure rate** (most stable switch).

Joining with `failed_transactions` reveals that **72.1%** of Kaveri Co-op Bank failures were coded as `NPCI_DECLINE_TIMED_OUT`, occurring primarily during peak evening hours (18:00 to 21:00), indicating severe server infrastructure bottlenecks.

## Python exploratory data analysis: Anomaly & fraud detection

Using Python (pandas, NumPy, matplotlib), we analyze the distribution of risk flags (`is_flagged = 1`) across ticket sizes and operating hours.

```python
import pandas as pd
import numpy as np

# Load clean transactions
df = pd.read_csv('transactions.csv').drop_duplicates(subset=['txn_id'])
df['txn_datetime'] = pd.to_datetime(df['txn_datetime'])
df['hour'] = df['txn_datetime'].dt.hour

# Calculate hourly flag rate
hourly_flags = df.groupby('hour').agg({
    'txn_id': 'count',
    'is_flagged': 'sum'
}).reset_index()

hourly_flags['flag_rate_pct'] = (hourly_flags['is_flagged'] / hourly_flags['txn_id'] * 100).round(2)
print("Late Night Flags (00:00 - 05:00):")
print(hourly_flags[hourly_flags['hour'].between(0, 5)])

print("\nDaytime Flags (10:00 - 18:00):")
print(hourly_flags[hourly_flags['hour'].between(10, 18)].mean())
```

### Anomaly Insights
1. **The Midnight Spike**: Between 00:00 and 05:00, the risk flag rate averages **6.48%**, compared to only **0.82%** during normal business hours (10:00 to 18:00), representing an 8x surge in suspicious activity.
2. **Merchant Risk Concentration**: Transactions processed by unverified merchants (`is_verified = 0`) trigger risk flags at **4.12%**, compared to **0.78%** for verified merchant partners.
3. **Ticket Sizing Velocity**: Transactions exceeding Rs 20,000 on unverified P2M merchant codes account for 41% of all high-confidence fraud alerts.

### Core DAX Measures

```dax
-- Payment Success Rate %
PaymentSuccessRatePct = 
DIVIDE (
    CALCULATE ( COUNTROWS ( CleanTransactions ), CleanTransactions[status] = "SUCCESS" ),
    COUNTROWS ( CleanTransactions ),
    0
) * 100

-- Technical Failure Rate % (Excluding User-Induced Insufficient Balance)
TechnicalFailureRatePct = 
VAR TechFailures = 
    CALCULATE (
        COUNTROWS ( CleanTransactions ),
        CleanTransactions[status] = "FAILED",
        RELATED ( FailedTransactions[failure_code] ) IN { "NPCI_DECLINE_TIMED_OUT", "BANK_SWITCH_OFFLINE" }
    )
RETURN 
DIVIDE ( TechFailures, COUNTROWS ( CleanTransactions ), 0 ) * 100

-- Flagged Transaction Volume INR
FlaggedVolumeINR = 
CALCULATE (
    SUM ( CleanTransactions[clean_amount] ),
    CleanTransactions[is_flagged] = 1
)
```

## 10 likely interview questions & model answers

### 1. How did you distinguish between technical failure and business failure?
I joined `transactions` with `failed_transactions` on `txn_id`. Failures coded as `INSUFFICIENT_FUNDS` or `INVALID_PIN` represent business/user failures where payment infrastructure functioned correctly. Failures coded as `NPCI_DECLINE_TIMED_OUT` or `BANK_SWITCH_OFFLINE` represent technical infrastructure defects.

### 2. How did you discover that Kaveri Bank failures clustered in the evening?
I extracted the hour from `txn_datetime` using `strftime('%H', txn_datetime)` and grouped by bank and hour. The failure rate for Kaveri Bank climbed from 2.8% during midday to 9.4% between 18:00 and 21:00, pointing directly to server capacity constraints during dinner peak traffic.

### 3. What caused NammaPay to have a 5.10% failure rate?
NammaPay's baseline performance was normal (2.2% failure rate), but it suffered 4 distinct server outage episodes lasting 30 to 45 minutes each. During those specific windows, failure rates surged to 38.7%, dragging down its overall annual average.

### 4. How did you handle the 100x transaction amount outliers?
I queried transactions where `amount > 100000` and evaluated merchant categories. Finding grocery purchases recorded at Rs 550,000 confirmed a two-decimal place logging bug. I normalized them in my SQL view using `CASE WHEN amount > 100000 THEN amount / 100.0 ELSE amount END`.

### 5. Why do night transactions have an 8x higher risk flag rate?
Between midnight and 5 AM, legitimate commercial retail activity drops sharply. Fraudsters exploit these low-monitoring hours to test stolen credentials, execute circular peer-to-peer transfers, and conduct rapid micro-transactions before cardholders wake up and freeze their accounts.

### 6. What DAX measures did you build in Power BI?
I implemented `PaymentSuccessRatePct`, `TechnicalFailureRatePct`, `FlaggedVolumeINR`, and `BankOutageDurationMinutes`, utilizing `CALCULATE()` and `DIVIDE()` to ensure responsive multi-dimensional filtering across banks, apps, and dates.

### 7. How does dynamic payment rail routing solve bank timeout failures?
When payment gateways detect that a primary bank switch's 5-minute success rate drops below 94%, the routing engine automatically re-routes subsequent transactions through secondary sponsor bank settlement rails, ensuring the end customer experiences a seamless checkout without manual retry.

### 8. What is the difference between P2P and P2M transactions in this dataset?
P2P (Peer-to-Peer) transactions represent transfers between individuals (no merchant ID), which carry zero commercial fees and lower fraud risk. P2M (Peer-to-Merchant) transactions involve commercial businesses, generate interchange revenue, and carry higher operational chargeback and sizing risks.

### 9. Why is Android payment success slightly lower than iOS?
The Android device ecosystem is fragmented across hundreds of budget hardware models, older Android OS versions, and unreliable webview browsers that occasionally fail SSL certificate verification during payment gateway redirects.

### 10. If you were deploying an automated alert for payment switches, what threshold would you set?
I would set a two-tier alert: a Warning notification if any bank's rolling 5-minute failure rate exceeds 4.0%, and a Critical PagerDuty incident if the failure rate exceeds 8.0% or latency exceeds 3,000 ms, automatically triggering the rail diversion protocol.
