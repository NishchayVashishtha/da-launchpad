## Learning objectives

- Sort rows with `ORDER BY`, ascending and descending.
- Sort by more than one column.
- Return the first N rows with `LIMIT`, and skip rows with `OFFSET`.
- Remove repeats with `DISTINCT`, and count unique values.
- Know why a tie-breaker column makes results stable.

## Why this matters for a Data Analyst job

<RealWorld>
"Top 10 restaurants by order value", "the 5 most recent hires", "which cities do we operate in?" These are everyday asks. Top-N lists and unique lists are the most common first outputs analysts share with managers.
</RealWorld>

## Concept

### ORDER BY

A table has **no guaranteed order**. If you do not write `ORDER BY`, the database may return rows in any order, and it can change between runs. Use `ORDER BY` whenever order matters.

```sql
SELECT product_name, mrp
FROM products
ORDER BY mrp DESC;
```

- `ASC` is ascending (smallest first). It is the default.
- `DESC` is descending (largest first).
- Several columns: `ORDER BY category ASC, mrp DESC` sorts by category first, then by price inside each category.
- You can sort by an alias, by a column position (`ORDER BY 2`), or by an expression. Prefer names over positions.

`ORDER BY` is one of the few clauses that **can** use a column alias, because it runs after `SELECT`.

### NULLs in sorting

In SQLite, NULLs are treated as the smallest value: they come first in `ASC` and last in `DESC`. PostgreSQL does the opposite (NULLs are largest). Where supported, `NULLS FIRST` or `NULLS LAST` makes it explicit. SQLite supports both from version 3.30.

### LIMIT and OFFSET

`LIMIT n` returns at most `n` rows. `OFFSET k` skips the first `k` rows. Together they give pages: page 3 with 10 rows per page is `LIMIT 10 OFFSET 20`.

`LIMIT` without `ORDER BY` gives "some n rows", not "the top n". For a top-N list, always sort first.

<Tip>
**Tie-breakers.** If two rows have the same value in the sort column, their order is undefined. Add a second sort column (usually the id) so results are the same every time: `ORDER BY order_value DESC, delivery_id`.
</Tip>

### DISTINCT

`DISTINCT` removes duplicate **rows** from the result.

```sql
SELECT DISTINCT city FROM restaurants;
```

With several columns, `DISTINCT` looks at the combination: `SELECT DISTINCT city, cuisine` returns each unique pair once. It applies to the whole row, not just the first column.

To count unique values, use `COUNT(DISTINCT column)`.

<Warning>
`DISTINCT` is also a quick way to discover messy data. If `SELECT DISTINCT city` shows `Mumbai`, `mumbai` and ` Mumbai`, you have found a cleaning job.
</Warning>

### Example 5: pagination with OFFSET

Rows 6 to 10 of the highest-value deliveries (page 2 when each page has 5 rows).

<SqlPlayground dataset="food_delivery" query={`SELECT delivery_id, order_value
FROM deliveries
WHERE order_value < 5000
ORDER BY order_value DESC, delivery_id
LIMIT 5 OFFSET 5;`} title="Page 2 of top deliveries" />

**Output:**

| delivery_id | order_value |
|---|---|
| 10006 | 2522.0 |
| 3713 | 2499.0 |
| 670 | 2385.0 |
| 6153 | 2379.0 |
| 4744 | 2367.0 |


We excluded values above 5000 because a few rows are data-entry errors (100x too big). Real analysts always sanity-check the top of a sorted list for outliers.

## Common mistakes

<CommonMistake>
**Using LIMIT without ORDER BY** and calling the result "top 10". It is just any 10 rows.
</CommonMistake>

<CommonMistake>
**Forgetting DESC.** `ORDER BY amount LIMIT 5` gives the five *smallest* amounts.
</CommonMistake>

<CommonMistake>
**No tie-breaker.** Two runs can show different rows when values tie, which confuses reviewers.
</CommonMistake>

<CommonMistake>
**Thinking DISTINCT applies to one column.** `SELECT DISTINCT a, b` is about unique pairs of (a, b).
</CommonMistake>

<CommonMistake>
**Using DISTINCT to hide duplicates caused by a bad join.** Fix the join instead. DISTINCT can mask a real error and slow the query.
</CommonMistake>

## Interview angle

<InterviewAlert>
"Top N" questions are everywhere. Mention ties out loud: "should ties share a rank or should I cut off at exactly N?" It shows you think about data, not only syntax. Ranking with ties comes later with window functions.
</InterviewAlert>

<InterviewQ q="What is the difference between DISTINCT and GROUP BY?">
For plain uniqueness they give the same rows: `SELECT DISTINCT city FROM t` equals `SELECT city FROM t GROUP BY city`. `GROUP BY` can also calculate aggregates per group (counts, sums), while `DISTINCT` only removes repeats. Use `DISTINCT` for a simple unique list.
</InterviewQ>

<InterviewQ q="Does a table have a natural order of rows?">
No. Relational tables are unordered sets. Without `ORDER BY` the result order is not guaranteed, even if it looks sorted today. Always specify the order when it matters, and add a tie-breaker column.
</InterviewQ>

<InterviewQ q="How would you return the 3rd page of results with 20 rows per page?">
`ORDER BY some_unique_sort LIMIT 20 OFFSET 40`. In SQL Server this is `OFFSET 40 ROWS FETCH NEXT 20 ROWS ONLY`. For very deep pages, OFFSET is slow because the database still walks past the skipped rows.
</InterviewQ>

## Key takeaways

- Without `ORDER BY`, row order is not guaranteed.
- `ORDER BY` supports several columns and `ASC`/`DESC` for each.
- `LIMIT n OFFSET k` gives top-N and pages. Sort first, add a tie-breaker.
- `DISTINCT` works on the full selected row. `COUNT(DISTINCT col)` counts unique values.
- Sorted lists and DISTINCT are great ways to spot outliers and messy values.
