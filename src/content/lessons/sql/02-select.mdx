## Learning objectives

- Write a `SELECT ... FROM ...` query from scratch.
- Choose specific columns and know why `SELECT *` is risky in real work.
- Rename columns with aliases (`AS`).
- Create calculated columns with `+ - * /` and functions.
- Use `||` to join text in SQLite.

## Why this matters for a Data Analyst job

<RealWorld>
A product manager asks: "Can you give me each product's name, its MRP, and the profit margin per unit?" You do not need Excel formulas. One `SELECT` with a calculated column gives it, and you can re-run it tomorrow on fresh data.
</RealWorld>

## Concept

`SELECT` is the command that reads data. Its basic shape:

```sql
SELECT column1, column2
FROM table_name;
```

- `SELECT` lists the columns you want.
- `FROM` says which table to read.
- The `;` ends the query.

<FormulaCard title="Basic query shape">
SELECT what-to-show FROM where-it-lives;
</FormulaCard>

### SELECT * and why to avoid it

`SELECT *` returns every column. It is fine for a quick peek. In real work, prefer naming the columns because:

- Tables can have 50+ columns. You only need a few.
- If someone adds a column later, your report may silently change.
- Fetching extra columns is slower on big tables.

### Aliases with AS

An **alias** gives a column (or table) a new name in the result. Use it when the name is unclear or when you create a calculated column.

```sql
SELECT mrp AS price_inr FROM products;
```

If the alias has spaces, put it in double quotes: `AS "Price in INR"`. Easiest habit: use `snake_case` with no spaces.

### Calculated columns

You can do maths on columns, row by row:

- `+`, `-`, `*`, `/` and `%` (remainder).
- Brackets work as in school maths.

The original table is not changed. The new column exists only in the result.

<Warning>
**Integer division.** In SQLite (and SQL Server), `7 / 2` gives `3`, because both numbers are integers. To get `3.5`, make one side decimal: `7 / 2.0`. MySQL and PostgreSQL behave differently (MySQL gives 3.5; PostgreSQL gives 3), so always be explicit.
</Warning>

### Joining text with ||

In SQLite and PostgreSQL, `||` joins pieces of text: `'Hello ' || 'Asha'` gives `Hello Asha`. If any piece is NULL, the whole result is NULL. You will see this again in the NULL and string lessons.

### Literals and expressions without a table

`SELECT` does not need a table: `SELECT 2 + 3 AS five;` works. It is handy for testing small ideas.

### A word on formatting

Put each clause on its own line and indent the columns. Readable SQL gets fewer bugs and better interview impressions.

<Tip>
Read a query in the order the database *understands* it: first `FROM` (which table), then `SELECT` (which columns). You will learn the full order in the HAVING lesson.
</Tip>

### Example 2: a calculated column with an alias

Profit per unit is MRP minus cost price. We round to 2 decimals so the output is tidy.

<SqlPlayground dataset="ecommerce" query={`SELECT product_name,
       mrp,
       cost_price,
       ROUND(mrp - cost_price, 2) AS profit_per_unit,
       ROUND((mrp - cost_price) * 100.0 / mrp, 1) AS margin_pct
FROM products
LIMIT 5;`} title="Profit per unit and margin" />

**Output:**

| product_name | mrp | cost_price | profit_per_unit | margin_pct |
|---|---|---|---|---|
| Masala Mandi Beverage 979 | 1289.0 | 922.17 | 366.83 | 28.5 |
| Ayurmitra Skincare 761 | 1069.0 | 646.31 | 422.69 | 39.5 |
| Lakshmi Home Decor 542 | 509.0 | 361.58 | 147.42 | 29.0 |
| Denim Dukaan Kurta 499 | 1599.0 | 1040.92 | 558.08 | 34.9 |
| Masala Mandi Dry Fruit 452 | 69.0 | 47.7 | 21.3 | 30.9 |


Notice `100.0`. It forces decimal division, so the margin is not rounded down to a whole number.

### Example 3: text with ||

Build a readable label from two columns. We use the retail `stores` table.

<SqlPlayground dataset="retail" query={`SELECT store_name || ' (' || city || ')' AS store_label,

**Output:**

| Vasudha Supermarket - Thane (Mumbai) | 15500 |
| Vasudha Hypermarket - Dwarka (Delhi) | 60600 |

| Vasudha Hypermarket - Whitefield (Bengaluru) | 89400 |


### Example 4: expressions without a table, and unit conversion

Delivery distance is in km. Let us also show metres, and the speed if a delivery took `actual_minutes`.

<SqlPlayground dataset="food_delivery" query={`SELECT delivery_id,
       distance_km,
       distance_km * 1000 AS distance_m,
       ROUND(distance_km / (actual_minutes / 60.0), 1) AS avg_speed_kmph
FROM deliveries
WHERE actual_minutes IS NOT NULL
LIMIT 5;`} title="Distance and speed" />

**Output:**

| delivery_id | distance_km | distance_m | avg_speed_kmph |
|---|---|---|---|
| 1 | 3.5 | 3500.0 | 4.3 |
| 2 | 3.3 | 3300.0 | 6.6 |
| 3 | 4.2 | 4200.0 | 7.2 |
| 4 | 1.6 | 1600.0 | 3.3 |
| 5 | 2.8 | 2800.0 | 5.6 |


We used a small `WHERE` to skip cancelled orders (they have no `actual_minutes`). The next lesson covers `WHERE` fully.

## Common mistakes

<CommonMistake>
**Putting a comma after the last column.** `SELECT a, b, FROM t` is a syntax error. Commas go *between* columns only.
</CommonMistake>

<CommonMistake>
**Integer division surprises.** `quantity / 2` on integers drops the decimal in SQLite. Use `quantity / 2.0` when you need the fraction.
</CommonMistake>

<CommonMistake>
**Using a column alias in WHERE.** `SELECT mrp * 2 AS double_mrp ... WHERE double_mrp > 100` fails in most databases, because `WHERE` runs before `SELECT` creates the alias. Repeat the expression or use a subquery (a later lesson).
</CommonMistake>

<CommonMistake>
**Leaving `SELECT *` in a final report query.** It works today and breaks tomorrow when the table changes. Name your columns.
</CommonMistake>

<CommonMistake>
**Mixing up quotes.** Text values need single quotes: `'Pune'`. Double quotes are for names.
</CommonMistake>

## Interview angle

<InterviewAlert>
A common warm-up: "Why should you avoid SELECT * in production queries?" Give two reasons (performance and fragility) and you sound experienced.
</InterviewAlert>

<InterviewQ q="Why avoid SELECT * in production queries?">
It reads every column, which wastes time and memory on wide tables. It is also **fragile**: if a column is added, renamed or reordered, downstream reports and code can break or change silently. Naming columns makes the query's intent clear and stable. `SELECT *` is still fine for quick exploration.
</InterviewQ>

<InterviewQ q="What is an alias and when do you use one?">
An alias is a temporary name given to a column or table using `AS`. We use it to make calculated columns readable (`price * qty AS revenue`), to shorten long table names, and to make result headers friendly for reports.
</InterviewQ>

<InterviewQ q="What does 5 / 2 return in SQL?">
It depends on the database. In SQLite and SQL Server, integer division gives `2`. MySQL gives `2.5000`. PostgreSQL gives `2` for integers. The safe habit is to write `5 / 2.0` or use `CAST(5 AS REAL) / 2` so your answer does not depend on the dialect.
</InterviewQ>

## Key takeaways

- `SELECT columns FROM table;` is the core of reading data.
- Name your columns in real work. Use `SELECT *` only for peeking.
- Aliases (`AS`) rename columns in the result and make calculated columns readable.
- Arithmetic works row by row. Watch out for integer division: use `2.0`.
- A calculated column never changes the stored table.
