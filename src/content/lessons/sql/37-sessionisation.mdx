## Learning objectives

- Explain what a session is and why it must be built in SQL.
- Use `LAG` to measure the gap to the previous event.
- Turn gaps into session start flags and then session numbers.
- Group events by session to get duration and size.
- Say what happens when you change the 30-minute rule.

## Why this matters for a Data Analyst job

<RealWorld>
Apps record clicks and events, not "visits". A product team asks "how long does a typical visit last?" or "how many sessions per user per week?". Nobody stored a session id, so you create one: events that follow each other closely belong to one session, and a long silence starts a new one. This is the standard way analysts measure engagement for apps, OTT platforms and websites.
</RealWorld>

## Concept

### The recognition cue

- "sessions", "visits", "a new session starts after 30 minutes of inactivity"
- "average session length", "events per session", "sessions per user"
- Any table of timestamped events and no session id

### The idea in four steps

Imagine a user's events on a timeline. A silence longer than the threshold cuts the timeline into pieces. Each piece is a session.

1. **Gap:** for each event, minutes since the same user's previous event (`LAG`).
2. **Flag:** mark an event as a session start if it is the first event or the gap is over the threshold.
3. **Number:** a running `SUM` of the flags gives each event a session number. The number increases by 1 at every start.
4. **Group:** `GROUP BY user_id, session_no` for start time, end time, duration and event count.

<FormulaCard title="Sessionisation template (30-minute rule)">
```sql
WITH g AS (
  SELECT user_id, event_time,
         (julianday(event_time)
          - julianday(LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time))) * 1440
         AS gap_min
  FROM events
),
f AS (
  SELECT user_id, event_time,
         CASE WHEN gap_min IS NULL OR gap_min > 30 THEN 1 ELSE 0 END AS new_session
  FROM g
),
s AS (
  SELECT user_id, event_time,
         SUM(new_session) OVER (PARTITION BY user_id ORDER BY event_time) AS session_no
  FROM f
)
SELECT user_id, session_no,
       MIN(event_time) AS session_start,
       MAX(event_time) AS session_end,
       COUNT(*)        AS events
FROM s
GROUP BY user_id, session_no;
```
</FormulaCard>

### Why the running SUM works

Say the flags for one user, in time order, are `1, 0, 0, 1, 0, 1`. The running sum is `1, 1, 1, 2, 2, 3`. Events 1 to 3 are session 1, events 4 and 5 are session 2, event 6 is session 3. The flag is the "new session begins here" signal and the running sum counts how many signals we have seen so far.

### Variations

1. **Different threshold.** Change `30` to `15` or to `1440` (a day).
2. **Duration.** `(julianday(MAX(event_time)) - julianday(MIN(event_time))) * 1440` minutes.
3. **Sessions per user per day.** Group by user and `date(session_start)`.
4. **Other databases.** In PostgreSQL use `event_time - LAG(event_time) OVER (...) > INTERVAL '30 minutes'`. In MySQL use `TIMESTAMPDIFF(MINUTE, prev, event_time)`. In SQL Server use `DATEDIFF(MINUTE, prev, event_time)`.

### Edge cases

- **First event of a user:** `LAG` returns NULL, and the flag must treat NULL as a start.
- **Exact duplicate events:** a repeated event has a gap of 0 and would not start a session, but would inflate event counts. Dedupe first.
- **Ties in time:** two events with the same second. Add a tie-breaker (`event_id`) in every `ORDER BY` inside windows.
- **A session that crosses midnight:** nothing special, as long as you use full timestamps, not dates.
- **Single-event sessions:** valid. Their duration is 0. Decide whether to count them.
- **Threshold rule:** a gap exactly equal to 30 minutes belongs to the same session if you use `> 30`. Say which one you chose.

<Tip>
The three-CTE structure (gap, flag, number) is the same every time. Learn it as a shape, and the specific question only changes the threshold and the final summary.
</Tip>

## Worked examples

### Example 1: gaps for one user

The subscription app logs events for each user. User 2 has eight events.

<SqlPlayground dataset="subscription" query={`WITH e AS (
  SELECT DISTINCT event_id, user_id, event_time, LOWER(event_name) AS event_name
  FROM events
  WHERE user_id = 2
)
SELECT event_id, event_time, event_name,
       ROUND((julianday(event_time)
              - julianday(LAG(event_time) OVER (ORDER BY event_time, event_id))) * 1440, 1)
         AS gap_minutes
FROM e
ORDER BY event_time, event_id;`} title="Gap to previous event" />

Output:

| event_id | event_time | event_name | gap_minutes |
|---|---|---|---|
| 1 | 2023-01-01 09:21:21 | signup | NULL |
| 2 | 2023-01-01 09:33:21 | trial_start | 12 |
| 25 | 2023-01-03 00:10:21 | search | 2317 |
| 34 | 2023-01-04 01:14:21 | app_open | 1504 |
| 93 | 2023-01-08 09:33:21 | trial_expired | 6259 |
| 118 | 2023-01-10 04:13:21 | app_open | 2560 |
| 195 | 2023-01-13 21:59:21 | content_view | 5386 |
| 208 | 2023-01-14 10:56:21 | content_view | 777 |


The first row has no previous event, so the gap is NULL. Events 1 and 2 are 12 minutes apart (one session). The next event comes more than a day later, so it will start a new session.

### Example 2: flag and number the sessions

<SqlPlayground dataset="subscription" query={`WITH e AS (
  SELECT DISTINCT event_id, user_id, event_time
  FROM events
  WHERE user_id = 2
),
g AS (
  SELECT event_id, user_id, event_time,
         (julianday(event_time)

### Example 3: sessions for a busier user

User 5 has 42 events. This app's events are spread over days, so here we use a one-day inactivity rule to see sessions with several events.

<SqlPlayground dataset="subscription" query={`WITH e AS (
  SELECT DISTINCT event_id, user_id, event_time
  FROM events
  WHERE user_id = 5
),
g AS (
  SELECT event_id, user_id, event_time,
         (julianday(event_time)
          - julianday(LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time, event_id))) * 1440
           AS gap_min
  FROM e
),
f AS (
  SELECT *, CASE WHEN gap_min IS NULL OR gap_min > 1440 THEN 1 ELSE 0 END AS new_session
  FROM g
),
s AS (
  SELECT *, SUM(new_session) OVER (PARTITION BY user_id ORDER BY event_time, event_id) AS session_no
  FROM f
)
SELECT session_no,
       MIN(event_time) AS session_start,
       COUNT(*) AS events,
       ROUND((julianday(MAX(event_time)) - julianday(MIN(event_time))) * 1440, 1) AS minutes
FROM s
GROUP BY session_no
ORDER BY session_no
LIMIT 10;`} title="Session summary for user 5" />

Output:

| session_no | session_start | events | minutes |
|---|---|---|---|
| 1 | 2023-01-01 10:01:30 | 2 | 87 |
| 2 | 2023-01-02 20:36:30 | 1 | 0 |
| 3 | 2023-01-08 11:28:30 | 1 | 0 |
| 4 | 2023-01-14 03:51:30 | 1 | 0 |
| 5 | 2023-02-01 04:43:30 | 1 | 0 |
| 6 | 2023-02-07 11:28:30 | 1 | 0 |
| 7 | 2023-03-03 09:37:30 | 1 | 0 |
| 8 | 2023-03-09 11:28:30 | 1 | 0 |
| 9 | 2023-03-22 04:11:30 | 1 | 0 |
| 10 | 2023-04-01 19:41:30 | 1 | 0 |


Now each row is a session with its start, event count and length. The threshold is only a parameter: the same query with `30` would split these into many one-event sessions.

### Example 4: the threshold changes the answer

How many sessions exist across all users if the silence threshold is 30 minutes versus a full day?

<SqlPlayground dataset="subscription" query={`WITH e AS (
  SELECT DISTINCT event_id, user_id, event_time FROM events
),
g AS (
  SELECT user_id, event_time,
         (julianday(event_time)
          - julianday(LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time, event_id))) * 1440
           AS gap_min
  FROM e
)
SELECT COUNT(*) AS events,
       SUM(gap_min IS NULL OR gap_min > 30)   AS sessions_30_min,
       SUM(gap_min IS NULL OR gap_min > 1440) AS sessions_1_day
FROM g;`} title="Sessions at two thresholds" />

Output:

| events | sessions_30_min | sessions_1_day |
|---|---|---|
| 36202 | 35603 | 28567 |


With a 30-minute rule almost every event is its own session, because this data has few quick back-to-back events. With a one-day rule the session count drops. Always state the threshold in your answer, because it changes the number a lot.

## Common mistakes

<CommonMistake>
Skipping the running `SUM` and grouping by the flag. The flag is only 0 or 1, so you get two giant groups per user, not one group per session.
</CommonMistake>

<CommonMistake>
Forgetting `PARTITION BY user_id` in `LAG`. Then the "previous event" can belong to another user, and sessions leak across users.
</CommonMistake>

<CommonMistake>
Not treating the first event as a session start. `LAG` gives NULL for it, and `NULL > 30` is not true, so the first session would never be flagged and the numbering would start at 0 or be wrong.
</CommonMistake>

<CommonMistake>
Subtracting timestamps as text. Use `julianday` (SQLite), `TIMESTAMPDIFF` (MySQL), `DATEDIFF` (SQL Server) or interval arithmetic (PostgreSQL).
</CommonMistake>

<CommonMistake>
Grouping by `session_no` only. Session numbers restart at 1 for each user, so different users get merged. Group by `user_id, session_no`.
</CommonMistake>

<CommonMistake>
Leaving duplicate events in the data. Repeats inflate event counts and can hide real gaps.
</CommonMistake>

## Interview angle

<InterviewAlert>
Sessionisation is a favourite at companies with apps. They want to see the gap, flag, running-sum chain. Say the three steps before you type. If you only remember one thing: the running SUM of a 0/1 flag creates group numbers.
</InterviewAlert>

<InterviewQ q="How do you assign a session id to events when there is none?">
I sort each user's events by time, use `LAG` to get the gap from the previous event, flag an event as a new session if it is the first or the gap exceeds the threshold (for example 30 minutes), and take a running `SUM` of the flag per user. The running sum is the session number, and I group by user and session number.
</InterviewQ>

<InterviewQ q="How would you find the average session length?">
After numbering the sessions, I group by user and session, compute `MAX(time) - MIN(time)` for each, and average those durations. I state that single-event sessions have zero duration, and I would show the result with and without them.
</InterviewQ>

<InterviewQ q="Why do we need PARTITION BY user_id in the window functions?">
Without it, `LAG` can pick the last event of the previous user, and the running sum continues across users. Sessions would be wrong at every user boundary. Partitioning restarts both calculations for each user.
</InterviewQ>

<InterviewQ q="Does the 30-minute threshold matter?">
Yes. It is a business definition, not a law. A shorter threshold makes more, shorter sessions, and a longer one makes fewer, longer sessions. I would confirm the definition with the product team and keep it as a parameter so I can show sensitivity.
</InterviewQ>

## Key takeaways

- Sessionisation = gap with `LAG`, flag with `CASE`, number with a running `SUM`, then `GROUP BY`.
- Always partition by user and order by time (plus a tie-breaker).
- The first event of a user is a session start.
- Number of sessions equals the sum of the flags; you only need the running sum to group.
- The threshold is a business choice. State it and show how it changes the result.
