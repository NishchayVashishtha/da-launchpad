## Concept

### What is a database?

A **database** is an organised store of data that many people and programs can read and update safely. Think of a big office cupboard. Each drawer holds one kind of paper: one for customers, one for orders, one for payments.

A **relational database** keeps data in **tables**. SQL (Structured Query Language, said "sequel" or "S-Q-L") is the language you use to talk to it. Popular relational databases are MySQL, PostgreSQL, SQL Server, Oracle and SQLite. The SQL you learn here works, with small changes, in all of them.

### Tables, rows and columns

A **table** is a grid, like an Excel sheet.

- A **column** (also called a field) holds one kind of fact, such as `city`. Every column has a **data type**: number (`INTEGER`, `REAL`), text (`TEXT`), date, and so on.
- A **row** (also called a record) is one thing, such as one customer.

Here is a tiny example of a `customers` table:

| customer_id | full_name | city |
|---|---|---|
| 1 | Rohan Patel | Bengaluru |
| 2 | Ramesh Patel | Chennai |
| 3 | Komal Patel | Delhi |

### Keys: how tables connect

Why not keep everything in one giant table? Because then a customer's name and city would repeat on every order. That wastes space and causes mistakes (change the city in one row, forget another). So we split data into separate tables and link them with keys.

- A **primary key (PK)** is a column whose value is unique for each row and never empty. `customer_id` is the primary key of `customers`. It is like an Aadhaar number: it identifies one person.
- A **foreign key (FK)** is a column in one table that points to the primary key of another. `orders.customer_id` points to `customers.customer_id`. It says "this order belongs to that customer".

### How SQL thinks

Most programming languages are **imperative**: you write the steps. SQL is **declarative**: you describe *what result you want*, and the database decides how to get it.

In Python you would loop over every customer, check the city, and append to a list. In SQL you write:

```sql
SELECT full_name FROM customers WHERE city = 'Pune';
```

You say "give me names of customers in Pune". You do not say how to scan or search.

Two more habits to build from day one:

1. **A query returns a table.** Always. Even `SELECT 1` returns a table with one row and one column. This is why you can put one query inside another later.
2. **Think in sets of rows, not one row at a time.** `SELECT price * 2 FROM products` doubles every row at once.

<Tip>
SQL keywords are not case sensitive (`select` = `SELECT`). Writing keywords in CAPITALS and column names in lowercase makes queries easier to read. Text *values* such as `'Pune'` are case sensitive in most databases, including SQLite when you use `=`.
</Tip>

### Example 4: is the primary key really unique?

The HR cheat sheet says the `employees` table has some duplicate rows. Let us test whether `employee_id` is unique by comparing total rows to distinct ids.

<SqlPlayground dataset="hr" query={`SELECT COUNT(*) AS total_rows,
       COUNT(DISTINCT employee_id) AS distinct_ids
FROM employees;`} title="Check key uniqueness" />

**Output:**

| total_rows | distinct_ids |
|---|---|
| 2412 | 2400 |


The two numbers differ, so `employee_id` is **not** unique here: a few employees are repeated. In a clean database the primary key is enforced. In real analytics work, you often meet tables where it is not, so always check.

## Common mistakes

<CommonMistake>
**Assuming an ID column is unique.** Always test with `COUNT(*)` versus `COUNT(DISTINCT id)` before you trust it. Duplicate keys silently inflate counts and totals.
</CommonMistake>

<CommonMistake>
**Using double quotes for text.** In standard SQL, `'Pune'` (single quotes) is text, and `"city"` (double quotes) is a column name. Some databases forgive double quotes for text, but not all.
</CommonMistake>

<CommonMistake>
**Forgetting that a query result is a copy.** `SELECT` never changes the stored table. It only reads. That is why you can experiment freely.
</CommonMistake>

<CommonMistake>
**Starting with a huge query.** Look at the table first (`SELECT * ... LIMIT 5`), then build step by step.
</CommonMistake>

## Interview angle

<InterviewAlert>
Interviewers often start with simple concept checks: "What is a primary key?", "What is the difference between a primary and a foreign key?". Answer in one clear sentence and add a small example from a business you know.
</InterviewAlert>

<InterviewQ q="What is the difference between a primary key and a foreign key?">
A **primary key** uniquely identifies each row in its own table and cannot be NULL, for example `customers.customer_id`. A **foreign key** is a column in another table that stores a primary key value to link rows, for example `orders.customer_id`. A table has one primary key but can have many foreign keys. Foreign keys are what let us join tables later.
</InterviewQ>

<InterviewQ q="Why do we split data into many tables instead of one big table?">
To avoid repeating data (called **redundancy**) and the mistakes that follow. A customer's city is stored once in `customers`, not on every order. Updates are easier and data stays consistent. The cost is that we must **join** tables when we need information from both.
</InterviewQ>

<InterviewQ q="What does it mean that SQL is declarative?">
You tell the database what result you want, and its **query optimiser** chooses how to run it (which indexes to use, in which order to read tables). This is different from Python or Java, where you write each step yourself.
</InterviewQ>

## Key takeaways

- A database stores data in tables made of rows (records) and columns (fields).
- A primary key is unique and never empty. A foreign key links a row to another table's primary key.
- SQL is declarative: describe the result, not the steps. Every query returns a table.
- Never trust that an ID is unique. Check it with `COUNT(*)` versus `COUNT(DISTINCT ...)`.
- Our 7 practice datasets are messy on purpose, to teach real-world habits.
